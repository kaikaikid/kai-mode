kai-mode使用手册

日常

开票与施工

一张票从“我想要”走到“已发货”，中间只有六步。你真正要做的，通常只是回答几个问题、拍一次板，然后等舰桥回报。

  1. 说需求

    把想要的东西用一句话说出来，交给舰桥。需求大、方向未定时，它会问你不超过五个大方向的问题，每题都带推荐答案；答完你拍一次板。

  2. 舰桥开票

    舰桥把需求整理成一张能执行的票：目标、验收标准、允许改什么、禁止改什么、怎么验证、依赖与红线。票会进 Issue。

  3. 你选普通还是加急

    普通 run 排队等槽位；加急 run 走预留槽，不抢普通 run。两种都只有舰桥一个发货口。

  4. 舰桥开 run

    舰桥执行 coding jump：一个 issue 一个 run，建独立 worktree 与分支，然后按任务图派子会话。

  5. 子会话施工 + 门卫审查

    施工子会话在 run 的 worktree 里改；门卫用另一段新上下文只读审查，逐条对 AC 出 accept / return。施工者不得自审。

  6. 舰桥发货

    舰桥在 G2 合并到 base、跑一次收尾门、push 一次、关票。这里只有舰桥能做。

三层，权限分得很死

角色只负责绝不做
舰桥对话、判断、开票、开 run、清场、发货、回报写产品代码、替用户做产品取舍
施工子会话按 brief 改代码、跑验证、提交到 run 分支push、合并、关票、改 state.json
门卫审查新上下文只读，逐条对 AC 出 accept / return复用施工上下文、替自己下结论
V2 内核状态推进、槽位、worktree、验收、发货规划与产品判断
为什么要分这么死

施工的人容易“觉得自己做对了”；所以审查必须换一段新上下文，不能自己审自己。舰桥独占推送和关票，是为了让“发货”只有一个出口。

你会看到什么

  • Issue 与 run 状态：票面写验收；.coding/runs/<run>/state.json 写阶段、任务、断点。状态只由 coding 写。
  • run 状态：谁在跑哪个 run、哪个任务、占哪个槽位；coding status 一眼看完。
  • 分支与提交：代码只在 run 分支里，不在聊天里；舰桥发货时才合并、推送。

卡住了会怎样

子会话超时或崩溃会自动重试；再失败转 blocked，保留产出。merge 冲突自动 rebase 一次；仍冲突转 blocked。红线（花钱、对外发布、不可逆、删未提交内容）只停当前 run，并且必须报人。

给技术同事：协议与判词

执行内核正本：v2/skills/coding/SKILL.md。关键是三段：

  • 子会话报告固定字段：result/files_changed/verification/open_questions/notes；报告与 diff 必须对得上。
  • 门卫审查：新上下文只读，逐条对 AC 出 accept / return 与证据；舰桥只认这个，不认主会话口头总结。
  • 隔离：一个 run 一棵 worktree、一个分支、一组 touchset；touchset 重叠的 run 排队。

入口：用户只跟舰桥说话；施工由 coding jump 起子会话。没有角色之间的唤醒，也没有塔台定时器。
