# 审批与权限

> 原则：**权限门禁是代码/流程，不是提示词。** 模型不能靠“我已经确认安全”绕过。
> 本文件只定义“谁可以做什么”；具体命令与门禁由项目 ADR/脚本落地。

## 一、自动允许（在租约与风险范围内）

- 读授权仓库、Issue、文档、代码、测试。
- 研究、写实现、跑测试/类型检查/lint。
- 创建任务分支与隔离工作树。
- 本地提交（`commit --only`，不卷他人文件）。
- 推任务分支（不是 dev/main），开/更新 PR。
- 更新票面进度、测试证据、检查点。
- 自动修复：最多 3 轮，同一错误 2 次即停。
- `direct` 模式下，`low`/`medium` 风险票在**所有门通过**后并入 dev。
- 试点期结束后，`low` 风险票可自动关闭；`medium` 是否自动关闭由项目配置决定。

## 二、必须人工审批

| 类别 | 例子 | 审批人 |
|---|---|---|
| 高风险数据 | 数据库迁移、删生产数据、不可逆转换 | 用户 |
| 公开契约 | 公开 API 变更、SDK 契约、对外协议 | 用户 |
| 权限/安全 | 修改审批策略、权限模型、凭据、安全边界 | 用户 + security |
| 治理 | 修改本框架的审批/角色/停机规则 | 用户 |
| 生产发布 | 部署、上线、对外真发布 | 用户 |
| 花费 | 付费执行体、云资源、第三方服务 | 用户 |
| 越界 | 超出票面租约、改他人文件、动未提交内容 | 用户 |
| 危险 git | force-push、删分支、绕钩子、重写历史 | 用户 |

**高风险票在审批前只能做研究与实现，不得落地/发布。**

## 三、风险分级与出货模式

| 风险 | `direct` 模式 | `pr` 模式 | `hybrid` |
|---|---|---|---|
| low | 自动并 dev + 关票（试点后） | 自动开 PR，可自动合并 | 同 direct |
| medium | 自动并 dev + 关票（门全过） | 自动开 PR，等人/自动合并按项目配置 | 同 direct |
| high | 停在 `ship_ready`，等人审批 | 开 PR，等人审批 | 开 PR，等人审批 |

`ship_mode` 由项目配置决定；本仓当前 `direct`，原因见 `docs/design-v1-absorption.md` §4.2。

## 四、审批记录

审批不是一个“好”字，必须可追溯：

```json
{
  "schema": 1,
  "ticket": 1854,
  "scope": ["path/a", "path/b"],
  "risk": "high",
  "approved_by": "user",
  "approved_at": "2026-10-21T17:00:00+08:00",
  "expires_at": "2026-10-22T17:00:00+08:00",
  "evidence": "issue comment URL / 拍板记录",
  "constraints": ["只允许改这两枚文件", "不得对外发布"]
}
```

- 审批绑定**票号 + 范围 + 风险**；范围变了审批失效。
- 审批有有效期；过期未执行 ⇒ 重新确认。
- 执行体必须把审批指针写进 `task-state-<票>.json`；Ground 出货前核验。
- 聊天里的“可以”不算审批，除非已回写票面/状态文件。

## 五、不得自批

- AI 不得修改审批策略，再用修改后的策略批准自己的工作。
- 写代码的 implementer 不得给自己出 `pass`；组主上下文不得代替 reviewer。
- 审批策略文件/权限配置的变更，必须单独开票、单独审批、与业务改动分离。
- 自动合并只在试点通过后开放，且限定 `low` 风险 + 全门通过 + 受保护分支。

## 六、阻塞与升级

- 需要审批 ⇒ 票状态 `blocked`，`blocker.approval_required` 写清“要谁批什么、批了会怎样”。
- 审批被拒 ⇒ `blocked`，不反复问同一个问题；把选项与代价写进日报一次。
- 安全拦截 ⇒ 立即停，不重试；通知用户；不允许换路径绕过。
- 红线（花钱/对外/不可逆/删未提交内容）永远先问，不因“会话有全权限”而自动执行。
