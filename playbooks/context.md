# 上下文与检查点

> 原则：**每个任务一个新上下文；状态不在聊天里，在文件与票面里。**
> 目标：长任务不因上下文塞满而失真；换班/崩溃后能恢复，但不把旧结论当真相。

## 一、只加载这些

- 项目规则中与当前任务相关的部分（不是整套治理文档）。
- 当前 Issue 正文与必要的前置票（只看依赖，不看全队列）。
- 相关 ADR/设计文档（按票面引用，不全文扫）。
- 相关代码与测试（按需读，不整仓读）。
- 最近一次检查点（`checkpoint-<票>-a<attempt>.json`）。
- 当前阶段的验收要求（AC 与验证命令）。

## 二、不加载这些

- 完整聊天历史、上一次会话的推理过程。
- 全部 Issue、全部 PR、全部项目文档。
- 与当前票无关的 diff、日报、台账。
- 别人的在制文件与未提交内容。
- 大 HTML/大日志全文（用路径/摘要/指定行）。

## 三、阈值

| 上下文使用 | 动作 |
|---|---|
| ≤65% | 正常工作 |
| >65% | 准备交接：写检查点、确认下一步、把证据落文件；不再新开大范围阅读 |
| >80% | 停止堆积：不再读大文件/长输出；保存检查点；结束本次尝试，交给新上下文 |

百分比以执行器实际可用容量为准；宿主不提供读数时，用**轮次/工具调用数**做代理阈值（例如只读 15–20 次、回执 ≤25 行），并在检查点写明“用代理阈值”。

## 四、检查点字段

```json
{
  "schema": 1,
  "ticket": 1854,
  "attempt": 1,
  "state": "validating",
  "branch": "exec/1854-v1-absorb",
  "commits": ["abc1234"],
  "done": ["合同落盘", "README 更新"],
  "tests": [{"cmd": "pytest ... -q", "result": "12 passed", "at": "..."}],
  "current_error": null,
  "next_action": "跑 reviewer 逐条 AC",
  "approvals": [],
  "artifacts": [".git/kai-scope/acceptance-1854.json"],
  "contract_sha256": "...",
  "saved_at": "2026-10-21T17:00:00+08:00"
}
```

字段见 `schemas/checkpoint.schema.json`。检查点可以比 handoff 长，但只给接任者读，不塞进组主上下文。

## 五、恢复时必须重新验证

旧检查点只是**线索**，不是事实。接任者按顺序重验：

1. 工作树在不在、分支对不对、有没有脏件。
2. 提交是否真实存在、是否在该分支可达、是否已并入 dev。
3. 检查点里写的测试命令**重跑一次**；读数以本次 stdout 为准。
4. 票面/审批是否有变化（合同哈希）。
5. 事件日志最后状态是否与检查点一致。

不一致 ⇒ `blocked`（reason=`checkpoint-mismatch`），写清哪一项对不上；不自行猜“应该是完成了”。

## 六、四种文件别混

| 文件 | 用途 | 长度 | 谁读 |
|---|---|---|---|
| `task-state-<票>.json` | 机器状态（状态/attempt/租约/合同哈希） | 小 | 脚本、Tower、Ground |
| `checkpoint-<票>-a<n>.json` | 进度快照，供接任者恢复 | 中 | 接任执行体 |
| `handoff-*.json` | 交接指针，触发下一角色 | ≤500 B | 启动器、接收方 |
| `acceptance-<票>.json` | 逐条 AC 证据 | 中 | reviewer 写，Ground 读摘要 |

**handoff 不写结论**；验收结论只住 `acceptance`。**状态卡不写长叙事**；叙事进日报一次。

## 七、token 预算

- handoff ≤500 B；只放 ID/路径/哈希。
- 状态卡四格；长叙事进日报一次。
- 子代理回执 ≤25 行；主上下文不复读过程。
- 验收只读摘要（`verdict`/`unverified`），失败才读细节。
- 不把票面全文、AC 原文、diff 反复粘进多个文件；用票号/路径引用。
- 省叙述，不省证据：证据可以长，叙述必须短。
