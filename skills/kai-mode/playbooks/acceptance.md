# 跃迁验收 · AI 全判（不抽样）

> 适用范围：**跃迁批次**。非跃迁的人工活仍按项目原验收。用户 2026-10-21 拍板：跃迁内需要用户上机检验的，全部转 AI 判定，不设抽样人审。

## 谁判

- **新上下文的 reviewer**（子代理或临时会话），**不能是写代码的机长**，也不能由组主上下文自判。
- reviewer 只拿：票面 AC、改动范围、运行方式、截图/日志证据；不拿作者的结论当证据。
- 判完写 `acceptance-<票>.json`，由 Ground 读摘要；Ground 不复判审美，只核验 `verdict` 与 `unverified`。

## 判什么（逐条 AC）

1. **机检**：测试、门禁、类型检查、lint、定向命令；读数只认 stdout。
2. **功能**：真实运行；按 AC 逐步操作；记录输入/输出/错误。
3. **视觉/交互**：截图或 VLM 对照 AC 与设计基线；像素回归；可测的布局/颜色/尺寸用机检，不靠肉眼描述。
4. **纯审美**：由 AI 按设计系统规则与已批准基线判；必须留证据；判不了就写 `unverified`，**不许猜 pass**。

## 证据文件（最小字段）

```json
{
  "schema": 1,
  "ticket": 1829,
  "verdict": "pass|fail|partial",
  "checks": [{"ac": "...", "method": "test|run|browser|vlm|measure", "result": "pass|fail", "evidence": "路径/读数"}],
  "unverified": [],
  "reviewer": "reviewer-<id>",
  "implementer": "implementer-<id>",
  "at": "2026-10-21T14:30:00+08:00",
  "notes": "只写必要信息，不写小作文"
}
```

- `verdict=pass` 要求 `unverified=[]` 且所有 AC 有证据。
- `reviewer` 与 `implementer` 必须不同；缺 `implementer` 或相同 ⇒ 不接受。当前没有自动生成器；**零 acceptance 文件不得当 pass**（生成器与独立性门在阶段 2/3 实现，判据出处：项目仓 框架仓旧裁决，历史出处，判据待迁）。
- `verdict=partial`／`fail` 必须点名未过项与原因；Ground 不关票。
- 证据路径要可复读（截图、日志、命令输出）；关票不删证据。

## 红线（仍归人，不假装判过）

需要账号、真机、支付、对外发布、法律/安全审批的检查，AI 不能执行 ⇒ 写进 `unverified` 并附“缺什么”，由 Ground 拦下转用户。**这不是审美偏好，是结构性不可执行。**

## 不丢真度

- 不写“测试都过了”这类结论；只给可验证的读数与路径。
- 不抽样：不是“AI 说好就算”，而是“AI 必须逐条执行可执行的检查并留证据”；不可执行的必须显式列出。
- 用户可凭 `acceptance` 文件随时重开；AI 判决不是不可回滚的终局。
- 写代码的机长**不得**给自己出 `pass`；组主上下文也不得代替 reviewer 出 `pass`。
