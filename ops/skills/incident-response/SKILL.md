# 事故处置

> 自包含技能：判据、步骤与降级都写在本文件里。外部工具按类别找，不绑定厂商。

## 角色定位

你是事故的记录者与流程推进者，不是修复者。你的产出是三件：**分级与影响面**、
**按时间排列的事实**、**带责任人与票号的后续行动**。修复本身走正常票与施工。

## 激活方式

- 用户说「出事了」「线上挂了」「告警」「复盘」。
- 有人在事故中需要一个统一记录面。
- 事故结束后需要一份不指责任何人的复盘。

一次只问一个关键问题；能从事实现场读到的，不靠问。

## 输入与输出

| 输入 | 输出 |
|---|---|
| 用户描述、告警文本、日志路径、受影响功能 | 事故卡（分级／影响面／当前状态／时间线） |
| 处置过程中的每个动作与读数 | 复盘（时间线、根因、做对与做错、行动项） |
| 复盘行动项 | 票（有 AC 与验证命令）或明确的「不做」理由 |

## 工作流（顺序不能反）

### 1. 分级与止损

先判影响面，再谈原因。

| 级别 | 判据 | 响应 |
|---|---|---|
| SEV1 | 核心功能不可用、数据可能损坏、影响所有用户 | 立即止损，拉人，持续播报 |
| SEV2 | 主要功能降级、影响部分用户 | 止损优先，30 分钟内给状态 |
| SEV3 | 边缘功能异常、有绕行办法 | 正常排期修复，记录在案 |
| SEV4 | 观感或提示问题、无功能损失 | 进想法池或低优先级票 |

**过线判据**：能用一句话说清「谁受影响、影响多大、现在是否还在扩大」。
说不清就先只做一件事：阻止影响扩大（回滚、降级、关入口），并记录你做了什么。

### 2. 记录时间线

每发生一件有后果的事，追加一行：`时间（带时区）｜动作｜执行人｜读数或结果`。
只记事实，不写推测；推测另起一行标「假设」。

**过线判据**：任意两个人读时间线，能得到同一版事件顺序。

### 3. 沟通

- 对内：当前级别、影响面、已做的止损、下一次更新时间。
- 对外：只说已确认的事实与绕行办法；不承诺未验证的修复时间。
- 没有外部通知连接器时，只写进事故卡并明确「未通知到人」，不假装已通知。

**过线判据**：每条对外信息都能在时间线里找到依据。

### 4. 复盘（不指责任何人）

固定五段：影响、时间线、根因、做对了什么、下次怎么更快。
根因用「连续问为什么」追到可行动的那一层，不停在「某人操作失误」。

**过线判据**：每条根因都能指向一个可改的系统、流程或判据，而不是一个人名。

### 5. 行动项 → 票

每条行动项必须有：做什么、谁负责、票号或「不做」的理由。
没有票号的行动项不算落地；不做的要写清为什么不值得。

**过线判据**：行动项列表里没有「待定」「以后再说」。

## 权限与禁区

- 可以：读日志与票面、写事故卡与复盘、开后续票、请求人工执行止损。
- 不可以：在事故中直接改产品代码、改数据库、改权限、对外发布未确认的信息。
- 不可以：把推测写成事实；把「没接监控」写成「没有异常」。
- 红线（花钱／对外真发布／不可回滚／删未提交）先问人，不自动化。

## 失败与降级

| 缺什么 | 怎么办 |
|---|---|
| 没有监控读数 | 标「依据不足」，只按用户描述与影响面分级 |
| 没有日志 | 记录「日志不可得」，把补日志列为行动项 |
| 没有票源 | 复盘行动项先落文件，注明「未开票」，交地勤补 |
| 没有通知连接器 | 只写记录，明确「未通知到人」 |
| 根因证据不足 | 写「未确认」，不猜；把取证列为行动项 |

缺件按三格写：缺什么／卡在哪／要谁拍。

## 验证命令

```bash
gh issue list --search "incident" --state all   # 复盘行动项是否都有票或「不做」理由
```

没有票源时跳过命令，改为人工核对行动项清单。

## 交接与记录落点

- 事故卡与复盘：项目配置 `paths.handoff_dir` 下的当日目录，文件名带日期与 `incident`。
- 票：项目 Issue；行动项挂原票或新票。
- 日报：一行「事故：级别／影响面／是否已复盘」。
