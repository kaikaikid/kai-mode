# 0034 职业/角色/团队三层分家 + 派生电话簿 + 四门验收口径

## Status

**accepted** —— 2026-11-11 用户拍板。

拍定依据：2026-11-11 频道讨论的定案；落点票面 `kaikaikid/kai-mode#20`（本 ADR 由该票产出）。
本 ADR 只定**三层定义与派生线**：不搬正文、不改任何正本文件、不改 doctor 判据。

正本层级：本 ADR 是这批口径的**裁决件**；字段级展开件住
[`docs/design/2026-11-13-role-layer-three-homes.md`](../design/2026-11-13-role-layer-three-homes.md)。
展开件不得与本 ADR 冲突，冲突以本 ADR 为准；两者都不造第二份词义定义（词义唯一家在 `GLOSSARY.md`）。

**项目专名的使用边界**：本 ADR 正文一律说「后端」；项目名与项目侧票号只出现在本 Status 出处段
与文末「下游与前置」两处。解耦门对 `docs/adr/` 的出处注记区有豁免，框架正本零专名。

## Context

- **现状一（职业与角色混层）**：框架侧一份 `roles/canon/<role_id>.md` 同时装「做什么」
  （mission/boundaries/workflow/output_contract 四块）与「是谁」（identity/personality 走 skins 与 persona）。
  换一张皮肤时没有机械判据能证明底座没被一起换掉。
- **现状二（团队层没有分家）**：团队名单在框架仓之外，成员组成、协作规则、每个岗位配哪些技能
  混在同一张表里；哪一行跟职业走、哪一行跟团队走，没有明写。
- **现状三（后端另存一份可写正本）**：后端侧存着角色卡正文 ＋ 版本快照，与框架侧正本并行，
  两处都能改，且没有单向的派生关系。这是「同一个语义两个家」的典型。
- **触发**：角色层要能被后端消费（后端要能回答「这个 role_id 是谁、归哪个柜」），
  但后端**不该**持有职责正文，也不该成为第二个可写正本。
- **冲突预检**：ADR-0033 D5（人格设定正本只读：改它要用户批准 ＋ 追加新版本 ＋ 保留旧版）
  与 D6（一份定义两用：通用职业名 ＋ 具名皮肤包）已拍板。本 ADR 是它们的**分家补充**，
  只引用、不推翻其中任何一条。

## Decision

### D0 三层各归其家

| 层 | 是什么 | 正本（唯一家） | 跟谁走 | 记忆关系 |
|---|---|---|---|---|
| profession 职业 | 基础能力底座：mission/boundaries/workflow/output_contract 四块 ＋ 技能清单 ＋ 档位（access_need/model_tier/effort） | `roles/canon/<role_id>.md`（当前 role_id 与职业一一对应）＋ 核心技能表（团队名单文件的「各角色核心技能」段）＋ `adapters/role-hosts.json`（档位投影） | 跟职业走；全员同一份，只读，改要升版 | 无记忆，只有只读引用 |
| role 角色 | 用户面的脸：叫什么、什么脾气、记得什么 | `roles/skins/{generic,guild}.json` ＋ `roles/persona/<role_id>.json`（`identity_core` 只读基线） | 跟角色走；换皮肤不换底座 | 唯一硬分区（role→peer） |
| team 团队 | 一整套班子：成员组成 ＋ 协作规则 ＋ 共享记忆根 | `~/Shared/kai-team/TEAM.md`（团队注册表待建，本 ADR 不建） | 跟团队走 | 团队层共享，治理日志按团队分账 |

三条边界说明（防「同一个语义两个家」）：

1. **role_id ↔ profession 当前一一对应**：每个职业恰好一个 role_id。反向映射表不建（见 R4），
   否则又多一个「谁是谁」的家。
2. **「叫什么」跨两层不跨语义**：通用职业名（发布面）在 `roles/skins/generic.json` 的 `name` 字段，
   具名皮肤名（酒馆面）在 `roles/skins/guild.json` 的 `name` 字段。同一职业可有多张脸，
   脸换名不改底座。
3. **同一个文件可以放两层的东西，但只能按区块分家**：团队名单文件的「各角色核心技能」段记职业侧的
   技能清单（跟职业走），「名单／协作规则」记团队侧（跟团队走）。同文件不同区块＝不同语义不同家。
   本 ADR 不搬家。

### D1 职业＝全员共用底座

- canon 四块（mission/boundaries/workflow/output_contract）**逐字不动**，是全员共用的一份底座；
  换皮肤、换团队都不改它。
- 档位三件（`access_need`／`model_tier`／`effort`）在正本里是**结构化判据**；
  宿主侧由 `adapters/role-hosts.json` 投影成宿主认的字段与值。宿主差异的唯一家是 `adapters/`。
- **不得**把 tier／effort 这类结构化判据降级成自由文本塞进后端的 `extra` 一类字段——
  降级＝判据不可机检＝门失效。
- 正本改动走升版（`canon_version` ＋ 指纹），改完必须重导出（见 D5 门 ①）。

### D2 角色＝每岗一张脸

- skin 与 persona 留在框架仓；一套皮肤一张脸，不进后端正文。
- `identity_core` 是**只读基线**：改它要团长批准 ＋ 追加新版本 ＋ 保留旧版，禁止覆盖
  （与 ADR-0033 D5 同一条纪律）。
- **`identity_core` 不进后端**：后端存一份 `identity_core` ＝ 第二个可写副本，
  而只读纪律在 upsert 写口上无法机械保证（写口能改就等于没有只读）。
- 角色＝唯一硬分区（role→peer）：查无角色必须报错，绝不静默落到用户级。
  这条**不因解耦而放松**。

### D3 后端角色系统只拆不删（逐件点名）

**留（运行时绑定件，拆完照旧工作）**

| 件 | 留的理由 |
|---|---|
| `RoleResolver` 存在性校验 | 查无角色必须报错（role→peer 硬分区） |
| `SessionBinder`（一 session 一角色） | 会话与角色的绑定是运行时事实，与正文无关 |
| 花名册（角色名／显示名目录） | 显示用目录，派生登记即可供 |
| `project:<id>` scope | 范围隔离按项目，不按正文 |
| `gateway_tool` 策略门 | 工具策略按角色档位执行，读的是档位不是正文 |
| `routines.role_id` 引用 | 例程引用角色 id，不引用角色正文 |
| exporter 渲染能力 | 渲染是出站能力，拆正本不影响它 |

**搬（内容正本，回框架侧正本）**

| 搬走什么 | 回哪一家 |
|---|---|
| 角色卡正文里的职责四块（mission/boundaries/workflow/output_contract） | `roles/canon/<role_id>.md` |
| personality 全文 | `roles/skins/<skin>.json` |
| `identity_core` 全文 | `roles/persona/<role_id>.json` |
| 版本快照（角色卡的 `versions/` 副本） | 不再当正本；改为按指纹对账 |

**为什么是「只拆不删」**：删掉上表任一运行时件，`bind_role`、按角色隔离的 `recall`、
`routine` 的角色引用会一起塌——那不是解耦，是拆桥。

### D4 派生电话簿：单向同步

- 后端那份角色登记表从「内容正本」**降级为只读派生登记**：只记「谁是谁、哪个柜」——
  `role_id` ／ 登记版本 ／ 正本指纹（canon_version ＋ canon_sha256，skin／persona 指纹） ／
  职业名 ／ 团队归属占位。
- **单向**：框架侧 registry → 后端派生登记。后端不回写框架侧正本；
  派生登记可弃可重建，正本不可弃。
- **写口收口**：REST／MCP 只留「读 ＋ seed」。seed 的唯一来源是 registry 文件（见 D5 门 ②）；
  禁止手改角色卡。
- 派生登记**不含**职责四块正文、personality 全文、`identity_core` 全文（与 R1「不搬正文」一致）。

### D5 稳定口径＝四门（缺一门票不关）

| 门 | 判据 | 不满足时的动作 |
|---|---|---|
| ① 版本不符即红 | registry 的 canon_version／sha 与派生登记不一致 | **拒绝绑定**并明确报错，不静默用旧的 |
| ② seed 只认文件哈希 | 来源只认 registry 文件哈希 | 手工写入即红，并留审计 |
| ③ UI 带版本角标 | 界面显示 registry_version ＋ sha | 对不上显示红 |
| ④ 旧柜只读归档 | 既有角色卡正文与旧记忆封存只读 | 不拆不迁；只读可查 |

- **缺任一门即判不稳，票不关**。四门是合取，不是四选一。
- 门 ① 的哈希口径按行尾归一后计算（同一份正本在 CRLF／LF 工作树下必须算出同一个指纹），
  否则行尾漂移会被复制进 registry。
- 门 ② 与门 ③ 是同一份哈希的两种用法：② 管数据入口，③ 管人眼出口。

### D6 本 ADR 不开的口子

**团队分支 ／ 账号分人（owner 列）／ project_registry ／ share** 四项**暂不开**，
等酒馆冒险团的结构做完另议。本 ADR 只定三层定义与派生线。

  - `#2012` 只读桥 ＋ 前端「角色与团队」管理页签（只读＋seed／核对）→ 落 D4 写口收口与 D5 门 ③。

票号属项目侧；正文一律叫「后端」，票号只出现在这一段。

## Consequences

- **好**：三层各归其家，一句话能问出「这条正住在哪」；后端拿到的是可机检的派生登记，
  不再是第二份可写副本；四门把「稳不稳」从感觉变成合取判据。
- **代价**：多一层派生与一道对账（每次改正本要重导出）；后端的角色查询从「读自己的库」
  变成「读派生登记」；四门任一没落地就判不稳，票压着不关。
- **本票不做**：不搬正文、不改任何正本文件、不改 doctor 判据、不加 owner 列、不建团队注册表、
  不建第二份角色表；registry 的导出实现归 #21。
