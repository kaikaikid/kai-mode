# 0010 角色唤醒围栏：角色之间不互相拉起

## Status

accepted —— 2026-10-24 用户令：「多个 agent 框架一起开发，得加一道围栏，以免角色之间互相拉起一堆新的回话窗口；相互拉起的设计后期再想方法设计」。

## Context

- 多个 agent 框架可能同时跑；一个角色自动唤醒另一个角色，会创建新的会话窗口，形成级联、成本与噪音。
- 塔台是独立岗位，定时器只是唤醒方之一（见 0003 演变注与 0006）；当前 kai-mode / 塔台仍有「自行判断拉起四角色」「拉起继任机长」的口径。
- 现在没有跨框架的唤醒协调机制；先收紧到人工可控，再设计相互拉起。

## Decision

### D1 角色之间不互相唤醒

`ground-crew`／`tower`／`pilot`／`copilot`／`kai-mode` 都不得创建或唤醒另一个角色的会话。
不自动、不代拉、不「继任」、不在发现别人停摆时自己开新会话。

### D2 允许的唤醒方

- **人工**：在任何宿主里手动执行 `/塔台`、`/机长`、`/副机长`、`/地勤`、`/kai-mode`。
- **宿主调度器／定时器**：只允许唤醒**塔台**，且只唤醒塔台；不得唤醒其它角色。
- 定时器不是角色，不参与角色间拉起；它唤醒的塔台实例仍走 0006 令牌互斥。

### D3 kai-mode 只推荐，不点火

`kai-mode` 入口只做路由与推荐：打印/写出唤醒命令（例如「请人工执行 `/塔台`」），交人工执行；
**不调用会话创建口，不自动起角色**。后续若放开，另立 ADR。

### D4 发现别人停摆时

塔台/机长/副机长发现另一角色停摆或断点：写日表备注、Issue 评论、播报；
由人工决定是否唤醒继任。**不自己开新会话**。

### D5 子代理不受本围栏约束

子代理是一次委派单元，不是角色会话；仍按 loop-protocol 每票 1 施工 + 1 审查、深度 1 层。
本围栏禁止的是「角色 ↔ 角色」的新会话，不是票内派工。

### D6 适配器的写法

`adapters/<宿主>.md` 可以描述宿主怎么起角色，但必须标注「**仅人工执行**」；
角色技能与协议正文不得写「角色自动调用会话口」。

### D7 未来放开

相互拉起需要新的 ADR：明确谁可唤醒谁、并发/预算/幂等/失败退避，并经用户拍板。
在此之前，本围栏是硬约束。

## 与既有判据的关系

- **0006 D3**：原「人工口令、kai-mode 入口、定时器」三路唤醒，按本 ADR 收窄为**人工 + 定时器**两路；
  kai-mode 只推荐命令，不再唤醒。0006 加演变注。
- **0003 D1**：「kai-mode 可自行判断拉起四角色」由本 ADR 废止，改为只推荐。
- **0006 令牌**：仍管塔台实例互斥；人工与定时器并发仍靠令牌，不因减少一路而失效。
- **loop-protocol §十二**：增加「角色之间不互相唤醒」一条，正文只留指针。

## Consequences

- 少一层自动化：塔台停摆不会被自动接替；人工看到日表/Issue/播报后决定是否唤醒继任。
- 换来不会出现角色互拉导致的新窗口风暴；多框架并跑时边界可预测。
- `set-kai-mode` 仍可安装塔台唤醒定时器，但只唤醒塔台；其它角色的启动回归人工口令。
- **这是规则 + canon 门，不是宿主级沙箱**：真正的运行时禁止要靠宿主权限层——装机时把会话创建工具从角色权限中移除，
  并在适配器回执里登记；做不到就如实写 `soft-permission-only`，不假装硬隔离。

## 验证

- `docs/canon.json` 的 `wake-fence` 键扫描 `skills/`／`agents/`／`README.md`，出现禁止的自动拉起短语即红。
- 手工：塔台发现机长停摆时只写记录/播报，不出现会话创建调用；kai-mode 只输出命令。
- `python scripts/doctor.py --with-tests` 全绿。
