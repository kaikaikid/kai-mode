# 0019 「停」与「等」分家：等待梯、续跑指针、裁决档改默认

## Status

accepted —— 2026-10-26 用户令（本会话）：「经常出现停下来的情况，帮我解决一下，在项目的规范里面调整，然后同步到 kai-mode 的设计里面」。
同向旧令：1024「不想自己动手」／1006「全自动」／0018 的起点「不要老是提问」。

## Context（病因，全部当场可复现，不是感觉）

- **E1 正本分叉，让已经设计好的「不停车」判据在本仓一条没生效。** 框架仓 `loops/loop-protocol.md` 已是 **v6**
  （0017：待发货即释位、换手点＝单票不是批、§七 停点闭集成文；0018：窗内取舍派裁决），
  而本仓 `D:\kaikaikid\workspaces\Kai-vass-Control\loops\loop-protocol.md` 停在 **v5**，
  且本仓 `scripts/loop-gate.py:7` 白纸黑字写「loops/loop-protocol.md（**v5** 唯一正本）」、
  `.ai/README.md`／`router.md`／`RULES.md` 全指向本仓那份。⇒ 角色启动读到的是旧版，改得再对也没人执行。
- **E2 协议自己写了一条与宿主执行模型冲突的禁令。** v5/v6 §八 都有「派活方必须收口……**不许以『等后台 agent』结束回合**」。
  但后台子代理的完成**只能靠通知唤醒**：回合不结束，回执就进不来。于是「等子代理」这一步在规范上无解——
  要么违规干等（还被 §八 另一条「15 分钟级长等＝违例」夹住），要么结束回合＝"看起来停了"。
  本会话实测：20 分钟内以「等子代理」收场两次，正是她看到的那类「停下来」。
- **E3 「等」的时候没活可派。** §八 只说「轮间干本地活（整理回执、写评论、复查日表）」，
  这三样几分钟就做完；做完以后规范里**没有任何一档**写着"接下来还能做什么"，剩下的自然就是停。
  而实际上那时通常还有：名额没满可以补票、下一张票的前提可以现量、只读巡检可以跑——都没被写成顺序。
- **E4 停下去的那一下没有留下"下一步是什么"。** 断点三件套（日表＋评论＋分支提交）记的是**已发生的事**，
  不记**待发生的第一动作**。所以每一次停，人或下一班都要从头重读一遍才知道卡在哪——停的成本被放大成"重新理解全场"。
- **E5 跃迁窗口绑在会话上。** 0018 D1「用户对某条会话说出『跃迁』⇒ 该会话进窗；会话结束即出窗」——
  继任班、定时器起的班、换宿主重开的会话一律在窗外，于是又回到「为取舍问人」或「写卡点停票」。
  而 0018 D2 早就把取舍题交给了裁决子代理：**「派裁决」这件事本来就不需要开窗**。

## Decision

### D1 「停」与「等」分家（协议 §七）

**停＝要人来推才走**（交班、宣布收工、把票挂在等人状态）。
**等＝回合可以结束，但状态没交出去**（子代理回执／定时器／下一轮会自己接上）。
两者只有一条共同硬要求：**结束时留下续跑指针**（D2）。
判据因此变成可核对的一句话：**没有指针的收场，无论嘴上说没说要停，对下一双眼睛都是停摆。**

### D2 续跑指针（协议 §七，新硬件）

任何停或等，收场前先落一行机读指针（≤8 行，落 Issue 评论——票面是唯一事实源），四件：
`等什么`（子代理／塔台／地勤／用户拍板）· `下一步第一个动作`（到命令或票号粒度）·
`在飞面`（票号、分支、HEAD sha、工作树脏否）· `接手能直接跑的验证命令`。
预算／上下文／轮次接近上限时**同样适用**（必要时加一份 `handoff/` 交接），不许静默消失。
指针不是第四件记录面，它只是「断点三件套是否可接」的判定项之一。

### D3 等待梯（协议 §八，取代旧「轮间干本地活」那一条）

等子代理时按序取**第一档还能做的**：① 名额未满＋日表有未完工行 → **补位开工**；② 下一张票前提逐量＋派工卡预热（只读）；
③ 只读量具／巡检跑一轮（回归切片、名册尺、门禁自测、票面 hold 普查），发现按「缺件三格」落票面；④ 补齐本票记录面；
⑤ 以上全空才做**有界轮询**（60–120 秒一轮，连续至多 3 轮，每轮之间重跑活性探测）；⑥ 到顶仍无回执 → 落指针＋播一次，按**两态收尾**收场。
配套把 E2 那条冲突禁令改写为：**A 态＝还在干**（梯上还有档就不收场）／**B 态＝挂等牌收场**（先指针后结束，并写明「这不是完工，在等 X」）。
旧「派活方必须收口——最终消息就是交付物」**继续约束子代理回执**（不许拿「我让后台去做了」当交付），不再用来要求机长焊在原地干等。

### D4 正身分叉收口（协议抬头）

协议**唯一正本＝框架仓** `tools/kai-mode/loops/loop-protocol.md`；项目仓那份＝**同哈希副本**，
只由同步步骤铺写，禁止两处各改一份。本仓的 `scripts/loop-gate.py:7` 与相关指针同步改口为「副本，版本以框架仓为准」。
**缺件登记**：两仓协议**哈希 parity 机检尚未实装**（该有它的位置＝`loop-gate` 或框架 `doctor`，二者谁先接谁写判据文案），
在此之前分叉只能靠人眼发现——E1 就是它没存在的代价。

### D5 裁决档改默认，窗口只管一件事（撤销 0018 D1 的会话绑定，0018 已加被订正指针）

**取舍题派裁决子代理＝机长／副机长的默认路径**，不再是"开了跃迁窗才用"。
「跃迁」口令只保留一个语义：**连续跑到日表清空、不逐票请示、不许以「这批做完了」当收班理由**（该语义 0017 已覆盖，此处不重复立法）。
窗外残留的「写卡点交塔台攒批」降级为**兜底**：只用于裁决子代理也判不了的两类题（两份都已生效的正本互斥／需人眼判观感），
这与 0018 D5 完全一致，因此**不新增状态、不落配置键、不写任何自动续期的授权档**——
给自己放行不在本 ADR 范围内（红线照旧先问）。

### D6 规范落点＝仓内文件，不落任何一家的会话记忆（2026-10-26 用户追加令）

用户同时用多家 agent 框架（Claude Code／Codex／workbuddy／Cursor…）做多项目，**判据必须对所有框架与所有机器同等生效**，
不许只活在某一家的记忆里。据此：

- **仓内三面**：`AGENTS.md`（各家自动读的入口，放"停与等分家＋续跑指针＋等待梯"的操作条款）·
  `.ai/rules/RULES.md` §3（同一条判据的规则位）· `.ai/rules/annex-host-neutral.md` **D10.1**（三层落点表＋回写口＋降级腿三件）·
  `loops/loop-protocol.md`（细则正本／本仓镜像）。四者只有**指针与粒度差异**，不各写一套数值（一次语义一个家）。
- **框架仓路径属本机私有**（`tools/kai-mode` 无 remote）：不得把它当"任何 agent 都能读到"的前提。
  协议抬头与本仓 D10.1 都写了降级腿——**读不到框架仓时，本仓那份即刻就是可读正本**，
  改动同批刷两份并把「未能回写」如实记进票面／日报，不许假装回写过、也不许因读不到就不改。
- **技能面本来就是跨框架的**：Magpie 库经符号链接铺 8 家（实测 2026-10-26：`.claude`／`.codex`／`.workbuddy`／
  `.workbuddy-ai`／`.cursor`／`.cline`／`.dsh`／`.qoder-cn` 各家 `skills/pilot/SKILL.md` 全部同为 2.7.0）。
  但**装体不是每家公司都有**——所以判据的最终承载必须是仓内文件，这正是本 D 存在的理由。

## Consequences

- 好的一面：她看到的「停下来」被拆成两类——**该等的**（有指针、有播、回执来了自动续）与**违规的**（无指针静默消失，可直接判违例）。
  「等的时候没活干」这一档被等待梯堵住，且梯的第一档正好压在最常被浪费的资源上（空着的名额）。
- 代价与风险：① 裁决档改默认＝**夜里代决的量上升**，代决清单必须照旧逐条落票面，可撤性由 0018 D6 的幂等与两次互否转上报兜住；
  ② 续跑指针多一次 Issue 写（每票每次收场一行），换来的是"接手不用重读全场"；
  ③ 本 ADR 只动文本与指针口径，**不新增记录面、不新增配置键**；
  ④ D4 的 parity 机检是**登记未做**——下次若再出现"框架改了、项目没改"，应先补量具而不是先吵判据。
