# 0025 塔台两把机械判据：待发货队列（ship-queue）与唤醒门卫（wake-gate）

## Status

accepted —— 2026-10-27 两件随塔台技能落地（0.31.0），2026-10-28 补记本 ADR（体检 M4：新机制无裁决记录）。

## Context

- 塔台每轮起手要回答两个问题：**有没有票要发**、**这一轮该不该起**。此前两者都靠模型读全文再判断：
  待发货状态散在 Issue 评论里，每次全量扫；定时器到点就拉一整轮会话，上一轮还在跑也照拉。
- 两件事都有明确的机械判据，可以放进脚本在模型会话之外跑，**零 token**；代价是判据从「正文里的几句话」
  变成「一段代码」，必须有裁决记录说明它凭什么这么判、失败时怎么降级，否则代码成了无主正本。
- 与 [0013](0013-installed-payload-no-dev-history.md) 的关系：判据的可执行正本随技能安装（脚本本身），
  裁决理由留本 ADR（ADR 不随装）。脚本正文只写判据与用法，不复述理由。

## Decision

- **D1 待发货队列＝派生物，不是记录面**（`airport/skills/tower/scripts/ship-queue.py`）：
  唯一事实源是 Issue 评论（首行 `verdict=pass`、第二行 `ac=n/m`）＋分支与提交在本地真实存在；
  每轮从源重算，只有「票还开着、sha 还在、没进 `origin/dev`」才留在 pending。不新增账本，
  机长不写、地勤不写，只有持牌塔台写 `paths.state_dir/ship-queue.json`（cursor 与缓存）。
- **D2 增量扫描带重叠窗口**：只拉 `updated_at` 变化的 issue 与其评论（`since=`，60 秒重叠），
  写前日志后再推进 cursor——cursor 丢了最多重扫，不会漏票。
- **D3 失败不冒充零票**：`gh`/`git` 调不通或限流 ⇒ `rc=3`；调用方（塔台或门卫）必须退回全量扫评论。
  `pending=0` 只能由「真的查到了、真的没有」产出。
- **D4 唤醒门卫在会话之外判**（`airport/skills/tower/scripts/wake-gate.py`）：定时任务 prompt 是薄壳，
  第一句跑门卫；判据顺序＝令牌心跳（他人持牌且未过本轮上限 ⇒ SKIP）→ 待发货非空 ⇒ WAKE →
  三张正常日表任一缺行 ⇒ WAKE → 探测失败 ⇒ WAKE。本轮上限＝`tower_cron.interval_min + 5` 分钟。
- **D5 跳过只回一行**：`rc=10` 时门卫只输出一行理由就结束，不读技能正文、不扫评论、不排班；
  这是「零模型调用」的唯一实现方式。
- **D6 人工唤醒不过门卫**：门卫只服务定时器。用户敲 `/tower` 就是明确要跑一轮。

## Consequences

- 塔台一轮起手的固定成本从「读全文＋扫评论」降到「跑两个脚本读一行」，零票轮几乎不花 token。
- 两把判据住在脚本里，改判据必须改代码并跑技能自带测试（`tower/tests/`），不能再靠改一句话。
- 门卫的探测失败一律放行：宁可多跑一轮空转，不可漏掉真有活的轮次——代价是失败态下门卫失去意义。
- 两件都依赖 `paths.state_dir` 与项目配置实例；实例读不到按缺件三格报，不猜路径。

## 验证

- `python scripts/doctor.py --with-tests` 全绿（含 `tower/tests/test_ship_queue.py` 等技能测试）。
- 零票场景：`ship-queue.py peek` 输出 `pending=0` 且 `rc=0`；限流场景：`rc=3` 且**不**输出 `pending=0`。
- 门卫跳过场景：上一轮持牌且心跳新于本轮上限 ⇒ `rc=10`，输出单行。
