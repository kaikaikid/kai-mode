# 0038 团长模板、职业/角色分层与项目冒险团

## Status

**accepted —— 2026-11-20 会长明确授权直接落地。**

本 ADR 统一“冒险者公会 / 项目冒险团 / 团长模板 / class_id / role_id / 副本 / 记忆最小单位”的口径，并部分取代旧 ADR 中“康娜＝唯一主代理”“profession 与 role_id 当前一一对应且反向映射表不建”的语义。

本 ADR 是规则正本；具体 Agent、频道、routine、飞书桥绑定、记忆权限或角色/职业正本的文件迁移仍须按本 ADR 的迁移清单与授权矩阵分步执行，未列文件的变更不被本条自动授权。

## Context

- ADR-0028 与 ADR-0033 建立了“唯一对话面 / 唯一主代理＝康娜”的入口模型，适合单项目、单团队阶段。
- ADR-0034 定义了 profession / role / team 三层分家：profession 住 `roles/canon/<role_id>.md`，role 住皮肤与 persona，team 住 `TEAM.md`；当时 `role_id` 与 profession 一一对应，反向映射表不建。
- ADR-0035 将可莉并回康娜，七位专业角色改为契约投影；ADR-0036 引入 `primary/core/specialist` 与 dispatch preset。
- 当前实际使用中出现两个长期项目并行（kai-mode、kai-vass）与潜在更多项目，单一康娜主代理会积累跨项目上下文，频道和 Agent 私有记忆也容易串味。
- 独立复核指出：原分团提案存在“职业术语双义、团队登记册重复真源、记忆 namespace 未解禁却写成前置、调度主体缺位、无验收判据”等问题。
- 会长已明确新方向：每个 L1 项目冒险团的调度者是“团长”；康娜的职能提炼为团长模板；康娜的人格/角色层作为人物卡“康娜”保留；`class_id` 表示职业模板，`role_id` 留给角色；可莉设为默认飞书前台。
- 守夜人作为值守职业/角色补入本模型：由项目冒险团按需配置，承担定时只读巡检、周度磁盘巡检与授权范围内的批量推送；只报读数与异常，不调度、不验收、不写产品代码。守夜人不得成为第二团长，也不得绕过团长的收口权。

## Decision

### D1 两层组织：L0 冒险者公会 / L1 项目冒险团

- **L0 冒险者公会**：通用框架与正本层。保存职业模板、角色人物卡、通用规范、宿主无关适配原则与记忆治理原则。它不是某个 Agent、频道或团队实例。
- **L1 项目冒险团**：一个长期项目对应一个团队实例。保存该项目的成员组合、团长实例、项目资料、运行实例、工具权限与记忆边界。
- 登记多少个长期项目，就建立多少个 L1 项目冒险团。短期、一次性任务不强制建立长期团队。
- 取消“副本地图 / 开放地图”作为正式组织层。若需要索引，只保留“团队登记册”作为逻辑索引，且不得与现有机器事实重复维护。

### D2 `class_id` 与 `role_id` 分家

- `class_id` 是 L0 职业模板 ID，回答“能做什么”：职责、边界、workflow、output_contract、工具档位、质量标准。
- `role_id` 是 L0 角色/人物卡 ID，回答“是谁”：身份、背景、关系、稳定人格、语言习惯与行为底线。
- 角色人物卡唯一，角色名唯一。新建角色由会长自行设计，不从模板批量复制人格。
- 一个 `role_id` 引用一个或多个 `class_id` 的配置关系由 L1 项目冒险团决定；具体绑定数量关系不在本 ADR 预设。
- 现行 `profession_id == role_id` 的派生登记迁移为显式 `class_id` 与 `role_id`；迁移前旧字段保持兼容读取，新写入只用 `class_id`。

### D3 `leader` 成为 L0 正式 class_id

- 在职业层新增正式 `class_id=leader`，定义“团长”职能模板。
- 团长职能包括：接单与项目判定、任务分诊、任务包派发、进度对账、验收取证、收口发货、人读汇报、待决与红线处理。
- 团长模板不写具体人格、口癖、背景、外貌或与用户的关系；这些属于 `role_id` 人物卡。
- 团长模板只定义职责边界与输入输出要求；团长的方法正文（预检卡、清场、发货、红线流程）唯一家仍是 `core/skills/gold/SKILL.md`，`class_id=leader` 只保留指针，不复制第二份方法正文。
- 康娜的人格/角色层从现有主代理中拆出，作为角色人物卡 `role_id=kona` 保留；该键迁移后对应现行 `coordinator` 人物卡，迁移前 `coordinator` 兼容读。其调度职能上提为 `class_id=leader`。
- ADR-0033 D2 的“唯一主代理＝康娜”在本 ADR 生效后改为“L1 每团有且仅有一位团长实例；康娜是 `leader` 模板来源与一个角色人物卡”。

### D4 团长实例与跨项目执行

- 每个 L1 项目冒险团有且仅有一位团长实例；该实例绑定一个 `class_id=leader`、一个项目角色人物卡、一个 Agent/Session 运行实例、项目工作区与记忆边界。项目角色人物卡引用同一个 L0 人物卡（按团可选不同皮肤），不新建角色。
- 推荐一项目一团长实例，不跨项目复用同一团长会话。
- 跨项目执行不由团长私下完成：
  1. 若只是查资料/评审/一次性任务，使用自包含任务包与 routine/独立 Session，不建立跨团长上下文；
  2. 若任务同时影响两个项目，由会长指定主项目，另一个项目提供只读证据或独立子任务；
  3. 若需要两个团长互相对话，必须显式开跨项目频道或临时协作频道，频道只在授权期间存在，结束后归档；
  4. 不允许把项目 A 的完整会话直接搬进项目 B。
- 默认不开常设跨项目频道；频道不是安全边界，只是协作容器。

### D5 可莉为默认飞书前台

- 可莉是目标态默认日常交流者与飞书前台，对接飞书桥：听懂人话、问清项目、结构化转接、回执排版、按明确要求读写日记。当前可莉 agent 仍处退场归档状态；恢复/新建与飞书桥绑定由单独变更授权执行，本 ADR 不自动实施。
- 可莉不是调度者：不派活、不验收、不改代码、不拍红线、不建独立记忆库。
- 工作请求进入可莉后转为结构化消息，至少包含 `project/team_id`、任务摘要、来源消息 ID、是否需要拍板；项目不清时只问一次。
- ADR-0035 D3“可将可莉人格并入康娜”与本 ADR 冲突时，以本 ADR 为准：可莉恢复为独立人物卡 “可莉”，职能单一且前台化。
- 飞书桥实现仍走 agent-autoloop；不恢复 ADR-0031 中已退役的本仓旧桥。

### D6 副本 = 单次任务/issue

- “副本”改为单次任务/issue 的用户可见说法，对应 `task_id`、run、验收与证据；不再表示项目团队或地图下挂区。
- “开刷”表示开始执行一个副本/任务；沿用 GLOSSARY 现行七步口径。“速推”沿用 GLOSSARY「快速通道／自动验收」定义，`fleet jump` 只作兼容别名；本 ADR 不改变速推的验收与发货语义。
- 取消“副本作为组织层级”不影响“开刷/副本运行”作为流程用语。

### D7 记忆最小单位改为“项目｜冒险团”

- 取消独立角色记忆：角色人物卡属于 L0 正本，不是记忆库；角色经历不再单独提炼为 role memory。
- 长期记忆逻辑分类收敛为：
  - `user`：会长偏好、红线、沟通习惯；
  - `shared`：已治理的跨项目方法与通用经验；
  - `project:<project_id>/team:<team_id>`：项目｜冒险团记忆，保存项目事实、团队约定、基线、坑；
  - `task:<run-id>`：任务过程记录、checkpoint、证据、未决项，结束归档，不自动晋升。
- 物理映射仍以 ADR-0037 D3 的 `project:<region-id>` 白名单为准；一项目一团时 `team_id=region-id`。当前物理 schema 不直接容纳 `project:<project_id>/team:<team_id>` 两级维度，放开一项目多团须先做 schema 升版 ADR。
- 角色经历如确需保留，只能作为带证据的治理条目写入项目｜冒险团记忆或经脱敏晋升到 `shared`，不得覆盖角色人物卡。
- 本 ADR 只定义逻辑归属，不承诺 Kai-vass 当前已实现 project/team namespace 隔离。V3.0 §21.6 的解禁门与 ADR-0037 状态继续有效；未接线、未解禁前不得声称隔离已经生效。

### D8 执行单元与模型组策略

- 执行单元按宿主能力选择，不把“临时冒险者”“Subagent”“助理/独立 Agent”混成一个概念：
  - **纯子代理**：宿主原生提供的短生命周期执行单元，适合一次性取证、审查、并行分片；上下文独立，只回摘要。
  - **拉起助理**：通过宿主 API 给另一个持久 Agent 发消息，适合需要长期角色身份、可续聊、可持有项目资料的固定团员。
  - **独立 Session/CLI 进程**：适合编程 Agent 中的干净起点任务；无原生子代理的宿主用它替代纯子代理。
- OpenBot 当前无原生子代理层：固定团员用 `send_message` / `kai-run.ps1` 拉起助理；怕偏见或一次性任务用 routine 独立 Session；不得假装存在原生 Subagent。
- Claude Code / Qoder / Copilot / Cursor 等有原生子代理的宿主：优先用纯子代理做一次性独立任务；固定团员是否渲染成 agent，由 `adapters/role-hosts.json` 决定。
- Codex / OpenCode 无原生子代理：用各自 CLI 的一次性进程或独立 Session；只要宿主命令能隔离上下文，就按执行单元策略选择，不跨宿主借兵。
- 任何执行单元都必须接到 L1 的 `task_id`、项目边界、工具权限与输出契约上；无法通过宿主能力审计的，标“未验证/不可依赖”。

模型组策略不在本 ADR 中预先绑定：

1. **通用原则**：`class_id` 不写厂商模型名、不预指定模型组。初始化新项目/新团时，由用户自行配置模型，或先与 AI 沟通后把决定写入对应团队/助理配置；未配置则复用主对话当前模型。
2. **OpenBot**：遵循助理自身设置，不在 `class_id` 上重复指定模型组。谁被拉起当助理，就用谁的 provider/model/reasoning effort；框架不伪造“已按 class 切模型”。
3. **编程 Agent**：默认同样复用主对话模型。若用户明确要求按职业/任务分流，允许在宿主适配层或团队配置中指定模型/模型组；该配置是项目/宿主实例事实，不写进 `class_id` 正本。
4. **缓存取舍**：频繁切模型会牺牲缓存收益，因此只有在用户明确配置或任务确有收益时才切换；本 ADR 不预设默认模型组。

因此，`class_id` 正本不持有模型配置；模型配置的唯一家是用户配置、具体助理设置与宿主适配/团队实例配置。

### D9 守夜人补入模型

- 在 L0 职业层纳入 `class_id=watchman`（守夜人）的目标态定义：按时只读巡检、周度磁盘巡检与授权范围内批量推送；输出只报读数、异常与必要动作回执。规则层已纳入，不代表职业正本文件与运行实例已创建。
- 守夜人可由每个 L1 项目冒险团按需启用；是否启用、推送权限、报告对象与排程由该团配置决定。
- 守夜人不是团长：不派活、不验收、不拍产品取舍、不写产品代码；推送范围之外的操作仍需团长/会长按现行授权流程批准。
- 守夜人的人格/角色卡唯一；若复用现有“守夜人”设定，只引用同一人物卡，不按项目复制人格。

### D10 真源与迁移

- 职业模板正本：`roles/classes/<class_id>.md`；从当前 `roles/canon/<role_id>.md` 的职责四块迁移。目标职业清单：`leader`（团长）、`ranger`（游侠）、`大法师`（大法师）、`artisan`（工匠）、`druid`（德鲁伊）、`scholar`（学者）、`dreamwalker`（梦境行者，创意联想/叙事构思/概念探索/非线性启发）、`shaman`（萨满，记忆治理/去重/冲突/来源/回滚）、`paladin`（圣骑士）、`watchman`（守夜人）；可莉前台职责作为 `front_desk`（前台）候选，是否独立成 class 待实施票确认。旧草案中把 `dreamwalker` 当记忆治理职业的语义迁移到 `shaman`。
- 职业名与角色/种族名分离：青铜龙是人物卡/种族，职业为 `shaman`；诺恩·星页是引用 `dreamwalker` 的人物卡，`dreamwalker` 不是记忆治理职业；矮人与铜须是人物卡/种族与氏族，职业为 `artisan`；卓尔是人物卡/种族，职业为 `ranger`；符文/奥术相关职业统一为“大法师”，`class_id` 与展示名均为“大法师”，不再使用“符文法师/奥术师/mage”作为职业名；瑞兹、康娜、可莉等具体姓名与外貌/背景只住人物卡。
- 角色人物卡正本：`roles/persona/<role_id>.json` 与 `roles/skins/<skin>.json` 的对应条目；只保留身份/人格/关系/语言，不再承载职业正文。
- 项目冒险团真源：`Shared/kai-team/teams/<team_id>.md`；`TEAM.md` 保留总览与 Agent 名单，`regions.json` 由团队真源同步或生成，避免两处手改。
- `role-registry` 派生 v2：显式包含 `class_id`、`role_id`、skin/persona 指纹、团队绑定占位；旧 `profession_id` 标 legacy。
- 旧概念进入 GLOSSARY 历史词条；迁移采取“保留历史、正本改名、索引更新”，不做硬删除。

## Consequences

- 好：职能、人格、项目、任务、记忆边界各归其家；多项目不再靠一个康娜上下文硬扛；可莉接飞书桥后，用户日常入口与项目调度分开。
- 代价：需要迁移职业正本、派生登记、GLOSSARY、ADR 与 Notion 提案；康娜/可莉相关 agent 与飞书桥绑定需要单独变更授权。
- 风险：把本 ADR 当成已批准规范会撞现行 ADR-0033/0034/0035；在宿主能力与记忆接线未核验前，不得承诺真正的会话/记忆/权限隔离。

## Alternatives

- 继续让康娜作为所有项目唯一主代理：否决。单入口省事，但长期多项目会累积上下文，正是本次要解决的问题。
- 每个项目复制完整八角色人格正本：否决。人格与职业会分裂成多份真源。
- 用频道名/角色名当隔离边界：否决。频道与名称不是安全边界，必须核验宿主权限与记忆过滤。
- 立即删除旧文件：否决。先保留历史与兼容读取，迁移验收通过后再单独审批清理。

## 验收前提

批准进入实施前必须完成：

1. 宿主能力矩阵：OpenBot 与各编程 Agent 的子代理/助理/独立 Session 支持情况；
2. 真源映射表：class/role/team/region/registry 的现存文件与迁移落点；
3. 记忆接线状态：Kai-vass MCP 是否接 OpenBot、namespace 读授权与治理过滤是否解禁；
4. 试点验收卡：跨项目资料注入反例、任务归档、团长唯一性、可莉转接不失真；
5. 授权矩阵：文档变更、agent 创建/修改、频道创建、飞书桥切换、记忆权限调整分别走哪道门。
