# 0003 机场体系重做：地勤／塔台／机长／副机长四角色与 30 分钟轮巡

## Status

accepted —— 2026-10-21 用户逐轮拍板并令「彻底重做机场体系……你自己梳理一遍，逻辑闭环就先清退旧的再部署新的」。本文是机场体系的唯一现行裁决；与旧裁决冲突以本文为准，旧件保留并在出处标注取代关系。

## 出处与迁移

重述自项目仓 `docs/artifacts/adrs/ADR-0137-airport-rebuild-four-roles.md`（2026-10-21）；它收编并部分取代项目仓 ADR-0131/0132/0133/0135/0136 的对应裁决（退役与保留清单见下）。本仓接管后本文为机场体系判据的正本，项目仓那份降为历史出处，不再约束本仓（见 0001）。入口、拷问、定稿一次拍板与审批红线的判据在 0002，与本文互指：本文 D6 的红线集＝0002 D7，本文 D1/D5 的发货边界落实 0002 D6 的「通行」判据。

## Context

旧体系的病不是一条规则写错，而是同一件事有多份互相矛盾的正本：

- push 权三处互斥：三份旧裁决各指一个持有者——谁都能引一条 accepted 裁决说自己能推。
- 塔台三种身份：对话主会话／两小时班／不 push 的协调组——叫「塔台」不知道叫谁。
- 令牌两层打架：一枚对两层、归属相反——在岗判定不可复现。
- 并发口径相反：并行作废对允许双飞——同一天两套排班。
- 跃迁链 8 条写死在多处文本——为凑数找活。
- 哨兵与闹钟三份正本三种节奏。

同时，主树长期有陈旧脏件、多个在制工作树与两次并车静默回退史：「不撞车」必须从规则层落到**物理隔离**层，不能靠会话自觉。

## Decision

### D1 角色与技能面（四角色＋三入口）

| 角色 | 口令 | 职责 | 权限 |
|---|---|---|---|
| kai-mode | `/kai-mode` | 所有剧本的统一入口与顶层抽象；可人工判断或自行拉起四角色；剧本不限于四角色 | 不执行具体活 |
| set-kai-mode | `/set-kai-mode` | kai-mode 的初始化安装：注入方法论与技能、装宿主适配器与定时器、doctor | 配置，不做日常施工 |
| 地勤 | `/地勤` | 跟用户对话、规划、开票、收 BOOM 想法（ideas/ 池与对应 issue） | 开票权；目前人工拉起，后期可定时 |
| 塔台 | `/塔台` | 每 30 分钟轮巡或人工：先发货、排班放本轮最后；合并、push、关票 | **独占 push**；不写产品代码 |
| 机长／副机长 | `/机长`、`/副机长` | 同一条 loop 的两个分支；goal 模式各管 2 张 issue＋6 个子代理 | 不 push；只管理不写码 |

- `loop` 不再作为用户入口，退为机长／副机长共用的参考正本。
- 四角色均可手动拉起或由 kai-mode 判断拉起；塔台额外可由 30 分钟定时器拉起。〔演变注：2026-10-23 起塔台的拉起权限由 [0006](0006-tower-token.md) D3 收紧——现阶段只许人工口令、kai-mode 入口、30 分钟定时器三路拉起，机长/副机长不得拉起/唤醒塔台；三路并发的跨进程互斥走 0006 D1 令牌。〕
- **宿主中立**：Qoder 用其定时口＋子会话；其他宿主由 set-kai-mode 探测后按同一契约装配，不写死 Windows 计划任务（0002 D5 的系统计划任务口径由此废止并推广）。

### D2 并发、名额与隔离

- **并发上限**：主、副机长各 2 张 issue 同时在飞，合计 4 张。每票 1 施工＋1 审查为固定口径；机动子代理按需拉起，**不设数量硬上限**，只受宿主容量与 token 预算约束。名额按机长独立计，不跨机长共享。〔演变注：原项目仓 ADR-0137 写死「每机长 6 个/合计 12 个」，项目仓 ADR-0141 已改为不设上限，本稿以现行口径为正本。〕
- **单写手**：同一张票同一时刻只有一个施工子代理在写；同一文件域不并行。
- **物理隔离**：所有写者（机长不写码；施工子代理）各用独立 git worktree 与分支；**主树只做合并与 push**，平时保持干净。工作树缺 `runtimes/`、依赖目录的坑按既定口径填：后端一律用主树正本解释器绝对路径；前端定向测例在树内离线安装依赖，**绝不软链主树依赖目录后跑包管理器**；全量前端腿由审查／塔台在主树合并后跑（环境三项自检＝绝对解释器、node、依赖，见 D8 新增）。
- **审查独立性**：审查子代理必须是新上下文，施工与审查不得同一上下文；写代码的不能给自己出 pass。

### D3 任务面：Issue ＋ 里程碑 ＋ 日表

- **唯一事实源**＝票平台上的 issue 正文与评论；**中央路线图票与所有 map 类票退役**，不再有中央路线图。
- **后备池**＝开放、带 `ready-for-agent`、挂了开放里程碑的票；排序按里程碑到期日（无到期日排最后），同里程碑内按票号。未挂里程碑的票不进后备池。
- **日表**：落项目仓配置面（由 set-kai-mode 初始化写入），一天一份、每机长一份、5–10 行；塔台写、不足 5 补、最多 10。日表只装排班视图，不装长叙事。
- **状态**：机长每完成一步写 issue 评论（开工／施工完成／审查完成／待发货／卡点）；**日表只由塔台写，状态只由机长写**——领取与记录分开，避免污染。
- **领取**：塔台把票写进日表即完成领取；机长按日表开工，不再另写租约。**不再有派单租约、跑道牌、信箱、交班条、签派单**。

### D4 一轮流程

1. 地勤与用户对话，把有价值但未成形的想法落 BOOM（ideas/ 池＋对应 issue），把可执行需求开成票（挂里程碑、`ready-for-agent`、写 AC 与禁区）。
2. 塔台每 30 分钟醒一次：**先发货**（本轮所有「审查通过」分支按票号合并进本地 dev，跑一次收尾门，推一次，关票）**再排班**（补日表到 5–10，给主副机长分票，放本轮最后一步）。冲突票退回机长，塔台不改代码。〔演变注：原项目仓 ADR-0137 D4 写「先排班、再发货」；2026-10 实践与塔台技能已反转为「先发货、排班放本轮最后」（`skills/塔台/SKILL.md`），本稿以现行口径为正本。〕
3. 机长 goal 模式：读自己的日表，同时最多开 2 张；每张派 1 个施工子代理（独立 worktree），写完派 1 个审查子代理（新上下文）逐条对 AC＋机检。审查不过 → 施工子代理 1 次修复，再不过退票／卡点。审查通过 → issue 评论写「待发货」。
4. 日表清空或踩红线 → 机长停。红线只停那一张票，其余继续；非必要不停车。
5. 恢复：新机长读日表＋该票 issue 评论＋分支提交，从断点续跑；不重写半成品。

### D5 塔台发货与边界

- 塔台是本仓**唯一**合并／push／关票持有者；机长、副机长、地勤、子代理一律不 push、不并 dev。
- 发货只认**审查子代理的判词**：issue 评论里 `verdict=pass` 且逐条 AC 有证据；塔台不重写代码、不替审查下结论。
- 批内合并、一次推送：收尾门跑一次；冲突票退回；push 后关票、写回执。推失败按回执点名重试，不绕钩子。
- **无删除合并路径**：本机安全删除层拦截带删除的合并，零删除的票才进自动发货；带删除的合并一律转人工拍板。（判据出处：项目仓 ADR-0137，历史，已由本条承接）
- **干净工位推送**：push 一律从干净临时工位发起（主树上下文会被 pre-push 门拦截），不绕门、不 force。（判据出处：项目仓 ADR-0137，历史，已由本条承接）
- 30 分钟周期是默认值；可人工 `/塔台` 立即拉起；周期可由 set-kai-mode 调整。旧四个 A/B、哨兵、塔台定时任务保持停用或删除，不得与新区块并存。

### D6 失败恢复与检查点

- 断点三件套：**日表（塔台写的排班）＋ issue 评论（机长写的状态与证据）＋ 分支提交（子代理写的代码）**。
- 不再有运行态 json、检查点文件、交班条作为运行态；长叙事只进 issue 评论与日报指针。
- 同一票失败 1 次重试；连续失败／卡点写 issue 评论并由塔台在下一轮决定重派或退回地勤；红线（花钱、对外发布、不可逆、删未提交内容）立即停该票并等人——红线全表见 0002 D7。

### D7 质量评分框架

保留评分框架（v13：6 科 36 项），**0 项因机场机器退场而替换**；7 项证据源重指（后端 pytest 存量红／flaky、前端 vitest、golden、本地 CI）；14 天节拍器迁到新宿主；全量评分约 16 分钟独占，安排在静默窗口或独立树，不与 4 issue／12 子代理并行撞车。

### D8 清退、改写与保留

- **整份清退（旧机场机器）**：班次目录与班次运行器（项目仓配置面）；在岗判定件与其测试；计划脚本的中转／排班段及其测试；旧看板生成段与板页；中央路线图票与所有 map 类票；lane 卡租约依赖。具体件清单见原 ADR §D8（历史出处）。
- **改写**：根说明；项目仓配置面（README／路由／规则／词汇表，由 set-kai-mode 写入）；单票闭环协议；就绪与工作树纪律检查脚本（A2 门换锚到日表／issue 评论）；板渲染；kai-mode 与 set-kai-mode。
- **新增**：四角色技能；项目仓配置面的日表目录；worktree 环境自检脚本（绝对解释器、node、依赖三项；缺件报错不静默）。
- **保留**：票＋里程碑体系；ADR（原件不删）；scope／docs／close／framework／loop 五门（A2 门换锚保留）；handoff 日报；质量评分框架。

### D9 迁移顺序（先清退旧的，再部署新的）

1. 冻结：旧定时任务全部停用；声明在制工作树不动；主树脏件不碰。
2. 裁决：本文提交；旧裁决加取代指针。
3. 清退：删旧件、改引用、A2 换锚；旧词 grep 清零＋过门禁。
4. 部署：写四角色技能与三入口；写日表目录；装 30 分钟塔台定时器并回读。
5. 试跑：用一张真票走完 排班→施工→审查→合并→push→关票；失败按 D6 处理。
6. 收尾：写 handoff，关重做跟踪票；后续项（评分证据源七项、主树脏件、旧看板清理）逐条登记。

## 退役与保留（取代明细）

- **清退（不再作为机制）**：五角色表；跑道／跑道牌／按跑道派单；两层令牌（在岗令牌）；派单租约与租约并行；信箱与信箱载荷；交班条；签派单；15 分钟哨兵与接力阶梯；两小时班次与 handoff 按铃；11 态运行态；检查点文件；六阶段顺序；8 条跃迁；机场生成物；A/B 双常驻机长与单在岗串行（由四角色取代）；「塔台不实体化」（塔台实体化为角色）；单令牌（随租约退役）；「不设常驻副机长」（副机长实体化为角色）。
- **保留**：平台路由；宿主中立；闹钟归 agent 装配；任务合同／DoR／DoD；执行三职；可靠性（去 TTL／租约）；审批矩阵；审计与既定偏离记录；AI 全判不抽样；日报四类边界；A2 门（换锚）；装机面边界（框架仓对项目仓）；机械票／新方向票边界并入地勤开票；剧本层在外；术语历史别名；WIP=4 与四角色目标一致；出货**单点原则**（持有者定为塔台，见 D5）。

## Consequences

- 正面：push 只有一个持有者，规则、脚本、技能三面同口径，引旧裁决推不出第二个 push 权；4 张在飞、12 个子代理上限写死，排班可复现；主树只合并/push、写者各 worktree，撞车面收窄；断点三件套换机长可续；红线只停票不阻塞其他票；旧件清退后引用同一套词。
- 负面／风险：塔台是 push 单点，停摆会积压——靠 30 分钟定时＋人工拉起兜底，塔台自身不写码降低故障面；4 票＋12 子代理对宿主并发与 token 有压力——先按上限跑一批，按关票数／撞车数调整；日表与 issue 评论是两套记录面，必须守住「塔台写表、机长写评论」的单写手，否则回到互相污染；旧裁决部分条款仍有效，须按取代明细逐条看，不能整份当废纸。

## 明确不做

- 不保留任何「第二 push 权」（机长、副机长、地勤、子代理一律不 push）。
- 不恢复跑道／令牌／租约／信箱／交班条／签派单／哨兵。
- 不让塔台写产品代码或替审查下结论。
- 不让机长写码或改任务表。
- 不用未提交脏件、force-push、绕钩子、对外发布或花钱来「先跑通」。
- 不在主树直接施工；所有写者各 worktree。

## 验证（判据级）

- 文档校验门通过（ADR 由 frontmatter 规则覆盖）。
- 工作树纪律检查在清退换锚后仍能通过。
- 旧词清零：活口文本里 grep 退役词（跑道牌、在岗、中转、15 分钟哨兵、8 条跃迁、签派单）仅剩历史／归档说明。
- 定时器回读：旧任务停用；新塔台任务启用、30 分钟。
- 试跑票：排班→施工→审查→合并→push→关票全链路有回执。
