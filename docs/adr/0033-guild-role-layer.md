# 0033 角色层重建：酒馆冒险团体系

## Status

**accepted** —— 2026-11-08 用户拍板。原话五条：

1. 「直接改家规」（不重写框架）。
2. 「家规放宽，所有框架都用这套角色子代理初始目标，**谁的康娜就在哪拉团队，不要老是白嫖别人的金币**」。
3. 「不拉别人家的 cli，但是要是本来自己就是命令行 agent 工具的话还是可以拉的」。
4. 「改成让青铜龙去读写改记忆」。
5. 「不用管版权，再给他一套通用的大众化的（类似视觉设计）职业名称模板」。

规范正本：Notion《冒险者酒馆 Agent 团队工程框架 V1.4》（`411c2f1c-a62c-8174-8250-dd16c79d7c04`）
＋子页《V1.5 最终版（AI 索引）》（`411c2f1c-a62c-8153-baf0-e72276e28941`）。
本 ADR 只裁决**框架侧怎么接**，不复述 Notion 正文；两者冲突时以本 ADR 为准，且不得放宽安全、审查独立性与用户最终验收权。

逐句冲突清单见 [`docs/design/2026-11-08-guild-role-layer-conflicts.md`](../design/2026-11-08-guild-role-layer-conflicts.md)。

## Context

- **现状与目标相反**：[0021](0021-plugin-playbooks-and-persona-retirement.md) D4 刚把人格层退役，
  [0028](0028-bridge-entry-and-airport-retirement.md) D1 明写「there are no other roles」，
  `adapters/README.md` 明写「执行侧只用宿主原生子代理，框架不拉 CLI 进程」。
  新体系要 8 个具名角色、要人格成长、要在没有原生子代理的宿主上也能跑。三条正面相撞。
- **底座已经在了**：把 V1.4/V1.5 涉及的 14 项运行时机制逐条对 `engine/coding/`，
  8 项已有、2 项部分、只有 4 项真缺（角色模板版本锁、权限交集引擎、记忆治理、风险分级驱动强制审查）。
  重写等于把踩过的坑再踩一遍，并重演 0028 Context 里「两套记录面互相不认识」那个事故。
- **宿主能力实测（Qoder，2026-11-08）**：原生子代理支持 `tools` / `disallowedTools` / `effort` /
  `hooks` / `isolation: worktree` / `maxTurns` / `timeoutMins` / `memory` / `model` / `permissionMode`；
  agent 文件的 markdown 正文＝子代理系统提示；`skills` 字段是**限制可用技能**不是注入技能；
  **随插件分发的子代理会被剥掉 `hooks` / `permissionMode` / `mcpServers`**，只保留 `tools` / `disallowedTools` / `isolation: worktree`。
- **Codex / OpenCode 没有原生子代理层**：现行口径下这两家永远登记 `no-new-context`，八角色装不齐。

## Decision

### D1 角色层合法化（取代 0021 D4）

框架重新定义**角色模板**：稳定的身份、职责、专业方法、行为边界与输出契约。
角色模板是版本化正本，不是「人格文件换个马甲」——区别在三点：

- 模板**不承载派活规则**。何时派、派几个、回执形状仍住 `engine/skills/fleet/SKILL.md`，模板里只留指针。
- 模板**不授予权限**。权限需求只是声明，实际权限按 D7 的宿主无关门禁 ＋ 宿主工具白名单取交集。
- 模板**唯一正本**，宿主上的定义文件是派生物（D4）。

0021 D4 的「删除 `agents/` 七个人格文件」保持历史事实不改；本条只废止它蕴含的
「框架此后不得定义 per-agent 角色」这一推论。

### D2 唯一主代理＝康娜；舰桥降为它的方法（取代 0028 D1 的「no other roles」）

- 对外仍然**只有一个对话面**，这一条不变（0028 的核心收益保留）。
- 这个对话面的角色名是**康娜**（通用职业名：协调调度）。`bridge` 技能不再是「角色」，
  而是康娜接单／清场／施工／发货的**方法正文**，继续按现名调用。
- 「there are no other roles」改为：**没有别的对话面，但有按需实例化的专业角色**。
  专业角色不是长期会话、不互相唤醒，[0010](0010-role-wake-fence.md) D1/D5 全部不变。

### D3 就地取材：本宿主自己的口可以用，别家宿主的口不可以拉

取代 `adapters/README.md` 的「框架不拉 CLI 进程」与 codex/opencode 两份适配器的「不退化去拉 `codex exec` / `opencode run`」。

| 情形 | 允许 | 说明 |
|---|---|---|
| 宿主有原生子代理 | 用原生子代理 | 首选，不降级 |
| 宿主本身就是命令行 agent 工具，且没有原生子代理 | 拉**它自己的**一次性进程 | Codex 里拉 `codex exec`、OpenCode 里拉 `opencode run` 合法 |
| 在 A 宿主里拉 B 宿主的 CLI | **禁止** | 例：Qoder 会话里起 `codex exec` = 白嫖别家金币，机械拦 |

- 判据一句话：**角色实例的入口必须属于当前宿主**。跨宿主借兵要另立 ADR 并经用户批准。
- 付费档（Codex）仍需显式授权，未授权记 `paid-not-authorized`，不偷偷跑——这条不变。
- 起不了任何新上下文 ⇒ 仍登记 `no-new-context`，**不许记「已审查」**，不退化成「主会话自己写代码」。

### D4 角色正本单一化：渲染 ＋ 指纹，不用指针

- 一份角色正本住框架仓（实施票定目录），含 identity / personality / mission / boundaries /
  workflow / output_contract 六块，头部记版本与内容 hash。
- 装机时**按宿主渲染**出该宿主的定义文件：正文逐字内联，frontmatter 按宿主字段映射
  （权限、模型档位、轮次上限翻译成宿主认的值）。
- 派生物头部记**正本 hash ＋ 版本**；巡检比对，手改派生物即报红。
- **不采用「宿主文件只放指针」**：正文＝系统提示，只放指针等于角色开局脑子里没人格，
  要靠子代理自己读一次才拿得到；工具白名单不含读工具就永远解不开，
  且读进来的是对话内容、会进宿主自己的压缩流程。防漂移靠「不许手改 ＋ 指纹巡检」，不靠指针。
- 角色文件**装项目级，不随插件腿**：插件形态下宿主会剥掉 `hooks` / `permissionMode` / `mcpServers`，
  且插件优先级高于项目级，会盖掉带门禁的那份。

### D5 记忆唯一写入者＝克罗米（通用职业名：知识管理）

- 人格设定正本**只读**；改它＝用户批准 ＋ 追加新版本 ＋ 保留旧版，禁止覆盖。
- 经验记忆是**追加式日志**，只有克罗米能读、写、改、回滚；其他角色只能提候选。
- 每条候选必须带来源、证据引用、before/after、回滚 id；单次对话与无证据的推断不得成为记忆。
- **不要求「宿主上下文压缩后按 hash 重注入人格全文」**：所测宿主的子代理钩子没有压缩事件。
  改为每次会话启动读只读正本 ＋ 校验 hash。V1.5 的 T04 按此改写，否则该阶段永远过不了。

### D6 通用职业名 ＋ 具名皮肤包

同一份职责定义，两套名字。产品仓发通用职业名，具名设定作为皮肤包挂上去；切换只换 identity 块，
职责／边界／输出契约**逐字相同**。

| 具名 | 通用职业名 | 管什么 |
|---|---|---|
| 康娜 | 协调调度 | 接单、分派、汇总 |
| 崔希丝 | 情报调研 | 外部资料、证据 |
| 瑞兹 | 架构分析 | 方案、取舍、根因 |
| 布莱恩·铜须 | 工程开发 | 代码、测试、修复 |
| 泰兰德·语风 | 视觉设计 | 插画、UI、风格 |
| 游学者周卓 | 文档写作 | 文档、教程、报告 |
| 克罗米 | 知识管理 | 记忆、复盘、经验 |
| 提里奥·弗丁 | 质量审查 | 独立验收、只判不修 |

用户已明确不做版权限制；本条只解决「一套定义两用」，不承载任何版权判据。

### D7 门禁押在宿主无关的三样上

宿主特有的工具白名单／钩子当**加分项**，有就更严，被剥掉也不塌。真正必须生效的是：

1. **工作区隔离**：每个可写角色一棵独立工作树 ＋ 分支（git 层，换宿主都吃）。
2. **范围校验**：交付时脚本对实际 diff 与授权范围，改了范围外的文件直接判退回（脚本层）。
3. **发货权单点**：只有主会话能合并／推送／关票，角色实例一律不发货（流程层）。

三样都已在 `engine/coding/` 跑着，不新造锁。审查独立性仍由「另一段新上下文」保证，不看角色文件名。

### D8 装机以文档为主，配一把薄校验尺

- 加一个宿主＝加一份 `adapters/<宿主>.md` ＋ 总则对照表一行，**不新增万能脚本**（沿用现行边界）。
- 但验收必须机械化。校验尺只做三件事：① 比派生物与正本指纹；
  ② 起一个只读角色真去写一次，必须被拒；③ 检查装机回执四步探测都有实测读数，没测的标「未测」。
- 现有 `core/skills/set-kai-mode/scripts/install-agents.py` 只有 Claude 落点一条腿，
  实施票补 Qoder 腿与渲染／指纹；不改成「覆盖所有宿主的大脚本」。

### D9 运行模型里区分三根轴

组织图保留八个人格，但运行时不是一个并列清单：

- **领域角色**（情报调研／架构分析／工程开发／视觉设计／文档写作）：竞争「主责任角色」，一个任务原则上一个。
- **质量门**（质量审查）：任何领域都要过，**不占主责任名额**，另计审查会话数。
- **平台服务**（知识管理）：任务结束后的后处理，**不占主责任名额**。

V1.5 的 TRIAGE 把三轴并列，导致「改 5 个文件 ＋ 高风险」同时命中 G03(M1) 与 G07(M6) 时，
按表头取 M1 ⇒ 角色会话上限 1 ⇒ 强制审查的第二个会话创建失败 ⇒ 死锁。
实施票必须补一条 mode/预算合成规则与此轴区分，并配测例。

## 实测发现（2026-11-08，Qoder Desktop CN）

装机后跑了三条探针，读数如下。它们不改判 D4/D7，但把 CAP 表里一句话划掉了。

1. **角色文件注册成「设备级 Agent」，不是子代理类型。** 用户级落点装进去的八份
   在 `list_agents` 里都能列出来，可用 `create_chat_session` 的 `agentId` 起会话；
   但 `subagent_type` 仍只有宿主内建的七个，按角色名派报 `Unknown agent type`。
   两种派发面要分开对待。
2. **工具白名单没有被执行。** 按 `agentId` 起只读角色（渲染出的 frontmatter 是
   `tools: [Read, Grep, Glob]` ＋ `disallowedTools: [Write, Edit, Bash, Agent]`），
   派它写一个临时文件——**写成功了**，`Write` 正常可用，同会话里 `Bash` 也在。
   ⇒ 该宿主该派发面 `readonly_hard = no`，C05 记 **MISSING**，按 `soft-permission-only` 登记。
3. **装完不等于可用。** 八份里初读有 4 份 `enabled=false / ready=false`，要用户侧启用。
   装机回执必须逐份核对 readiness，不能只看文件写成功。

**为什么不改判**：D7 本来就规定门禁押在宿主无关三样（工作树隔离／范围校验／发货单点）上，
宿主工具白名单只当加分项。这次实测只是证明「加分项这次没加分」——
凡是 C05 非 HAVE 的宿主与派发面，审查独立性只能靠**另一段新上下文 ＋ 只读副本 ＋ 范围校验**，
不能靠 agent 定义文件里的 `tools`。反过来说，如果当初把只读押在白名单上，这套体系今天就漏了。

## Consequences

- **好**：八角色在六家宿主上形状一致；人格有唯一正本与指纹，漂移可机械抓；
  门禁不押在会被剥掉的宿主钩子上；复用现有内核，不产生第二套状态面。
- **代价**：多一层渲染与指纹巡检；`install-agents.py` 要加宿主腿；
  角色文件必须装项目级，装机步骤比「随插件一把装」多一步。
- **本票不做**：不建角色目录、不写八份 ROLE.md、不改任何安装面技能正文。
  那些随实施票同批改 ＋ 同批同步中央库，避免只改仓内造成库副本漂移。
  逐件待改清单（含精确行号）住冲突清单文档。
- **基线红不归属本票**：开工前 `python scripts/doctor.py --with-tests` 已是
  28 项／绿 23／红 5（`plugin-manifest`、`pointer-targets`、`skill-tests`、`install-sync`、`install-receipt`），
  工作树干净、HEAD `655c727`。本票验收判据＝**红集不扩大**，不认领也不修既有红。

## 验证

- `python scripts/doctor.py --with-tests`：红集与基线逐项相等（项数以 stdout 汇总行为准）。
- `docs/canon.json` 的角色层判据键**随实施票登记**：现在登记会打在推迟改的安装面引句上，
  把当前绿的 `canon-dup` 变红；实施票把那些降为指针时同批登记，并配反向测例。
- 冲突清单里每条「本票已改」项，回原文重读确认旧句已不在或已加指针。
- 实施票的验收标准见 Issue #7（AC-01…AC-08），本 ADR 只覆盖 AC-01。
