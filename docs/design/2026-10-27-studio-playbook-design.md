# 创作体系三坊两台设计记录
> kai-mode 的创作、施工、验收、分发与看板
2026-10-27

## 一句话

**三坊**管「写什么、怎么做、怎么收」，**两台**管「怎么发、怎么看」。三坊不互相代写判据，两台只读与分发，不改状态。

## 三坊

| 坊 | 管什么 | 对应件 | 硬边界 |
|---|---|---|---|
| **剧本坊** | 写剧本：一个剧本一个插件，角色是命令，步骤是技能 | `.claude-plugin/marketplace.json`、五个插件目录（`airport`／`core`／`board`／`intake`／`ops`）、`PLAYBOOK.md`、`commands/`、`skills/` | 不执行具体活；判据只写一份，别处留指针 |
| **施工坊** | 按票施工：取票、开工、派施工、增量提交 | 单票闭环 `loop`、机长／副机长／王牌技能、`ticket.py`／`card.py`／`worktree.py` | 只管理不写码；单写手；不 push、不合并 |
| **验收坊** | 独立审查与发货：新上下文出判词，塔台分批发货 | 审查判词、`round.py`、塔台技能、收尾门与推送工位 | 施工者不得自审；塔台独占 push 与关票；门自身成本不算票的红 |

### 剧本坊

- 一个剧本＝一个插件；插件自带两份 `plugin.json`（Claude Code／Qoder）、`PLAYBOOK.md`、`CONNECTORS.md`、`commands/`、`skills/`。
- 角色命令只做「读取并执行」，不写长规则；长规则只住技能正文。
- 技能写成可执行步骤：触发 → 步骤 → 每步过线判据 → 做不下去怎么降级。
- 新剧本先定「谁用、什么时候用、不做什么」，再写步骤；没有角色的剧本不进 `airport`。

### 施工坊

- 一张票一条闭环，三个车道复用同一份 `loop`，只换车道参数（`main`／`deputy`／`ace`）。
- 工作树按车道：`lane-main`／`lane-deputy`／`lane-ace`；票在树里换分支，不为每张票新开树。
- 机械判断先跑脚本：票面、回执、判词、续跑指针、车道树；脚本判不了的取舍才读协议那一节。
- 停点只认协议 §七 那五类；「停」与「等」分家，收场先落续跑指针。

### 验收坊

- 审查必须是另一段新上下文；施工者不得给自己出 `pass`。
- 判词首行 `verdict=pass|fail`，第二行 `ac=<通过数>/<总数>`；`pass` 才进「待发货」。
- 塔台按票面文件重叠分批，跑一次收尾门、推一次、关票；推送用登记过的临时工位，用完即拆。
- 门超时／性能耗尽记「没跑成」并打印读数，不折成被审对象的红。

## 两台

| 台 | 管什么 | 对应件 | 硬边界 |
|---|---|---|---|
| **分发台** | 钉版本、装宿主、体检 | `marketplace.json`、`plugin.json`、`manifests/plugins.lock.json`、`install-profiles.json`、`plugin-check.py`、CI | 只发布已过体检的插件；不改技能正文 |
| **看板台** | 只读展示：日表、票、分支、交接 | `board` 插件的 `flight-info`：SQLite ＋ 板配置 → `board.json`（AI 读）＋ `index.html`（人读） | 只读；不改票面、不改日表、不代写记录 |

### 分发台

- 市场清单是唯一清单；插件版本与内容摘要钉在锁文件里，漂移即红。
- 装机档位：`core` 最小闭环，`full` 全部自动件；手动件单独装。
- 体检先跑 `plugin-check`，再跑仓级 doctor；红了先修清单或重钉，不写「大概没问题」。
- 宿主先保两条腿：Claude Code 与 Qoder；Codex／OpenCode 留骨架。

### 看板台

- 一块板＝一个 SQLite 库 ＋ 一份板配置 ＋ 两个产物；源按类型插件式增删。
- 车道默认 `main`／`deputy`／`ace`；王牌日表只读，塔台不写。
- 任一源失败只降级点名，不整页崩；AI 只读 `board.json`，不 grep HTML。

## 一条需求的流转

```text
需求
  → 剧本坊：选剧本／补步骤（没有就新开一个插件）
  → 施工坊：开票 → 日表 → 车道树 → 施工 → 增量提交
  → 验收坊：新上下文审查 → verdict → 待发货 → 塔台分批发货
  → 分发台：钉版本 → 体检 → 装到宿主
  → 看板台：只读展示在飞、待发货、卡点与收尾
```

## 参考源记录

**KWP 原项目（anthropics/knowledge-work-plugins）已作为高优先级参考源完成核对，参考工作到此收口。**

- 借的：插件／市场清单的分发形态；技能的「触发词＋步骤＋验收判据＋连接器降级」写法；版本钉死与 CI 体检。
- 没借的：18 个业务插件、MCP 连接器内容、记忆／任务看板；`tech-debt` 与 `testing-strategy` 也不吸收（已有 `harness-audit`／`tdd`／审查门）。
- 结论：KWP 与 kai-mode 重合约一成且全在知识层；kai-mode 的执法层（工作区隔离、独占 push、票状态机、五道门、审计账、红线、续跑指针、定时唤醒）KWP 没有。
- 后续不再把 KWP 当待办参考源；新需求按本仓 ADR 决策，不回头照抄上游。

相关件：[ADR-0021](../adr/0021-plugin-playbooks-and-persona-retirement.md)、[插件化架构图](2026-10-27-kwp-plugin-architecture.svg)。

## 明确不做

- 本记录只落文档，不做实现；不新增脚本、不改协议、不改看板。
- 不把三坊两台写成新的人格层；角色仍是命令，判据仍住技能与协议。
- 不恢复 `registry.json`、人格文件或一票一树。
- 不引入 KWP 的业务插件与连接器内容。
