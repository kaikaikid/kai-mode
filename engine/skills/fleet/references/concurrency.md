# 并发与槽位

## 数量

| 维度 | 默认 | 上限 | 开关 | 计数口径 |
|---|---|---|---|---|
| run（一次开工） | 1 | 3 | `--ships N` | 按 run 集合独立计 |
| 子代理（Crew，并发） | 按 ready 任务数（上限 5） | 5 | `--crew N` | 按 run 集合独立计 |
| Worker（单任务可拆子任务） | 不主动拆 | 8 | — | 每张任务独立计 |

- Crew 与 Worker 不是同一种计数：Crew＝run 内同时活跃的子会话上限；Worker＝单张任务
  可拆的执行单元上限。设计规则是 Worker 不突破 Crew（`min(worker 上限, crew_limit)`）。
  **该钳制当前预留、未接线**：内核无任务拆分数入口，`clamp_workers` 是带测试的纯函数、
  无生产调用方，也无 `worker_clamped` 事件写入方（见 `docs/schema.md` 未实现清单）。
- 并发是天花板，不是目标：默认 0 个子代理，康娜能直接做完的不派；派之前报「几个、为什么、上限几」。
  机械／单一活 ≤1 个，标准施工 ≤3 个；只有真实并行、互不重叠的子问题才并行。

- `--ships N` 一次创建 N 个 run，各自 worktree ＋ 分支，共享 `fleet_id`（`<宿主>-<时间戳><后缀>`）。
- 混搭开团与速推时，给多条命令传同一个 `--fleet <ID>`，总数仍受上限约束。
- 不同康娜／不同 agent 框架互不抢占槽位；但 **touchset 冲突检测是全局的**。
- 用户说「开团 2 队」「晚上用 3 队」→ 翻译成 `--ships N`，不问第二遍。

## 排队

并发满时新 run 进 `queued`；槽位空出后自动提升（`promote_queued`）。
`--tasks` 可在开 run 时直接写任务图，不必等 run 起来再 plan。

## 重试预算

- 子代理重派：同一任务 1 次。
- `return` 上限：3 轮。
- 失败重试：2 次。
- merge 冲突：自动 rebase 1 次。

预算是硬上限，不是目标。第三次尝试之前先换方法（`diagnosing-bugs`）。

## 目标分支与自动关票

- push 目标默认 `dev`；仓里没有 `dev`（例如已经并入 `main`）则用当前分支。
- 任务文本里的 `#123` 或 GitHub issue URL 会在发货时自动关票；识别不到就跳过，不阻塞发货。

## 吞并外部成果

`fleet assimilate <branch> --approve` 把别的分支成果并进来。
**必须用户先同意**：这条命令会改写当前 run 的 baseline，属于不可逆面。
